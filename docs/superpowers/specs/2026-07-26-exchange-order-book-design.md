# QuickShop Exchange 中央订单簿设计

- 日期：2026-07-26
- 状态：设计已确认
- 目标版本：首个单服可用版本，并为未来跨服撮合预留边界

## 1. 背景

大型 Minecraft 服务器中，贵重物品和廉价物品都可能因为供给、需求或短时间集中交易而出现剧烈价格变化。固定价格商店不能反映全服供需，也缺少统一的成交记录、流动性和风险控制。

本功能新增一个中央交易所。玩家将货币与同质化物品存入交易账户，通过真实订单簿提交买卖订单。交易价格由买卖双方的挂单与撮合自然形成，系统不保证物品保值，也不使用公式强制决定长期价格。

## 2. 已确认的产品决策

1. 使用真正的中央订单簿，不使用自动做市公式。
2. 中央交易所和现有 QuickShop 箱子商店并存。
3. 交易所作为独立的 `addon/exchange` 模块交付。
4. 货币和物品都先存入独立交易账户，再用于挂单。
5. 支持限价单和带最大滑点保护的市价单。
6. 采用价格优先、同价时间优先的连续撮合。
7. 采用 Maker/Taker 手续费。
8. 市场 24 小时连续交易，并提供价格笼子与波动熔断。
9. 只交易可完全互换的同质化物品。
10. 普通物品默认按 `Material` 建立市场；特殊物品由管理员映射至独立市场 ID。
11. 首版只运行一个撮合节点，但领域模型和仓储接口不依赖 Bukkit，以便未来迁移到跨服服务。

## 3. 目标

- 提供透明、可审计的全服物品订单簿。
- 通过真实买卖挂单完成价格发现。
- 支持部分成交、撤单、冻结资产和离线结算。
- 在任何正常失败、重试或服务器重启后避免重复订单、负余额和超卖。
- 将数据库、撮合和统计工作移出 Bukkit/Folia 游戏线程。
- 提供足够的价格保护，防止误操作和短时间异常波动。
- 保留现有箱子商店行为，不自动迁移或改写已有商店。

## 4. 非目标

首版不实现以下能力：

- 止损单、止盈单、冰山单、融资、融券或杠杆。
- 玩家之间的证券、股份或公司所有权。
- 独特装备、随机属性装备、装有物品的容器等非同质化资产。
- 自动将箱子商店转换为交易所订单。
- 复杂 K 线 GUI 或网页交易终端。
- 多撮合主节点、跨服共识或自动故障转移。
- 自动处罚关联账户；首版只生成可审计的异常告警。

## 5. 模块与组件

新增 Maven 模块 `addon/exchange`，生成独立附加插件。它依赖 QuickShop API，并复用现有用户、物品匹配、经济、菜单、语言和平台调度能力。

### 5.1 `MarketRegistry`

读取市场配置并提供不可变的市场定义：

- 市场 ID、显示名和标准物品指纹。
- 计价货币。
- 基准价、绝对最低价、绝对最高价和最小报价单位。
- 最小交易数量、最大单笔数量和账户限额。
- 手续费、价格笼子、滑点和熔断参数。
- 是否禁止该物品创建普通箱子商店。

配置分为两类：费率和风险限额可以热重载，只影响新订单，开放订单继续使用其保存的费率版本；物品指纹、计价货币、价格精度、最小报价单位和最小交易数量属于结构性配置，只能在市场为 `PAUSED` 且不存在开放订单时修改。这样不会让同一订单簿同时存在两套精度或物品定义。

### 5.2 `ExchangeAccountService`

管理玩家和系统账户的货币余额。每种计价货币分别维护：

- `available`：可提现或用于新订单的余额。
- `frozen`：已被开放订单或待处理提现冻结的余额。

余额使用 `BigDecimal`，禁止使用 `double`。货币精度由市场的计价货币定义。

### 5.3 `CustodyService`

管理玩家在各市场的标准化物品数量：

- `available_quantity`：可提现或用于新卖单。
- `frozen_quantity`：被开放卖单或待处理提现冻结。

同一市场只接受与市场标准指纹完全匹配的物品。交易所内部只记录数量；市场配置保存用于提现重建物品的标准模板。

### 5.4 `OrderService`

验证并提交下单、撤单和查询请求。所有写请求必须携带唯一 `requestId`，重复请求返回第一次执行的结果，不创建第二个订单。

### 5.5 `MatchingEngine`

每个市场拥有一个串行命令队列和一个订单簿。撮合领域对象不得引用 Bukkit 类型、玩家对象、世界或背包。

订单簿使用按价格排序的数据结构，每个价格档内部使用 FIFO 队列。目标复杂度为插入和撤单 `O(log n)`，获取最优价格 `O(1)` 或 `O(log n)`。

### 5.6 `RiskService`

在订单进入撮合队列前执行账户、价格、数量、频率、自成交和市场状态检查。撮合提交前再次检查相关订单和余额版本，防止并发状态变化绕过验证。

### 5.7 `LedgerService`

所有货币与物品变化使用不可修改的复式账本记录。每个 `journalId` 至少包含一组借方和贷方分录；同一资产的分录总和必须为零。更正操作只能追加反向分录，不能修改历史分录。

### 5.8 `ExchangeRepository`

提供市场状态、账户、库存、订单、成交、账本、转账和行情仓储接口。SQLite 实现服务于单服首版；MySQL 实现用于正式大型服务器和未来跨服部署。

### 5.9 `ExchangeUI`

负责命令、Inventory GUI、权限和本地化。UI 只调用服务接口，不直接执行 SQL 或修改订单簿。

## 6. 领域模型

### 6.1 市场

一个市场由 `marketId` 唯一识别，并绑定一个标准物品和一种计价货币。例如：

- `minecraft_diamond/default_currency`
- `custom_silver_ingot/default_currency`

同一物品使用不同货币交易时，必须创建不同市场。

市场状态包括：

- `OPEN`：接受订单并撮合。
- `HALTED`：熔断，只允许撤单和查询。
- `PAUSED`：管理员暂停，只允许撤单和查询。
- `RECOVERING`：数据库或内存状态正在恢复，不接受写操作。
- `CLOSED`：永久关闭，不接受订单；关闭前必须处理或撤销开放订单。

### 6.2 订单

订单至少包含：

- `orderId`：UUIDv7 或同等全局有序唯一 ID。
- `requestId`：客户端幂等 ID。
- `marketId`、`accountId`、`side`。
- `type`：`LIMIT` 或 `MARKET`。
- `timeInForce`：限价单为 `GTC`，市价单为 `IOC`。
- `limitPrice` 或市价单滑点边界。
- `originalQuantity`、`remainingQuantity`。
- `status`：`OPEN`、`PARTIALLY_FILLED`、`FILLED`、`CANCELLED`、`REJECTED`。
- `prioritySequence`：市场内单调递增的时间优先序号。
- 创建时间、最后更新时间、市场配置版本和费率版本。

修改开放订单必须按“撤销旧订单并创建新订单”处理，因此会失去原时间优先级。部分成交不会改变剩余订单的时间优先级。

### 6.3 成交

每笔成交包含唯一 `tradeId`、市场、Maker/Taker 订单、双方账户、成交价、成交数量、双方费率、双方手续费、撮合序列号和服务器时间。

## 7. 数据表

表名使用 QuickShop 数据库前缀，逻辑表如下：

- `exchange_markets`
- `exchange_market_state`
- `exchange_accounts`
- `exchange_inventory`
- `exchange_orders`
- `exchange_trades`
- `exchange_ledger_journals`
- `exchange_ledger_entries`
- `exchange_transfers`
- `exchange_request_results`
- `exchange_candles_1m`
- `exchange_audit_alerts`
- `exchange_schema_version`

账户和库存表包含版本列。MySQL 使用行锁和唯一约束保证余额与订单幂等；SQLite 使用单写事务。所有金额和价格使用定点十进制列，所有物品数量使用非负整数。

关键约束：

- `available >= 0`，`frozen >= 0`。
- `available_quantity >= 0`，`frozen_quantity >= 0`。
- `remaining_quantity` 位于 `0..original_quantity`。
- `(account_id, request_id)` 唯一。
- 同一市场的 `priority_sequence` 和撮合序列不可重复。
- 账本分录不能更新或删除。

## 8. 撮合规则

1. 买单按价格从高到低排列。
2. 卖单按价格从低到高排列。
3. 同价订单按 `prioritySequence` 从小到大排列。
4. 新进入的订单是 Taker，订单簿中的订单是 Maker。
5. 买单价格大于或等于卖单价格时可以成交。
6. 成交价采用 Maker 的挂单价格。
7. 一笔订单可以跨多个价格档部分成交。
8. 限价单剩余数量按 `GTC` 继续挂单。
9. 市价单按 `IOC` 执行，无法在滑点范围内成交的剩余数量立即取消。
10. 同一账户的订单相遇时拒绝或取消新进入的一侧，不产生成交和手续费。

### 8.1 资产冻结

- 限价买单冻结 `限价 × 数量 + 最大可能 Taker 手续费`。
- 市价买单根据当前盘口和玩家确认的滑点上限计算最大金额；盘口为空时拒单。
- 卖单冻结对应的标准物品数量。
- 撤单、拒单和未成交市价单立即解冻剩余资产。
- 成交后释放买单未使用的价格差额和多余手续费预留。

### 8.2 手续费与舍入

买卖双方手续费都以计价货币收取。Maker 使用 Maker 费率，Taker 使用 Taker 费率。手续费按货币精度向上舍入，成交金额按市场精度精确计算。

买方支出为成交金额加买方手续费；卖方收入为成交金额减卖方手续费；双方手续费计入系统费用账户。系统费用账户可由管理员提现到税务账户或永久销毁，但提现同样必须经过转账日志。

首版不支持负 Maker 费率或返佣。

## 9. 价格与行情

行情维护：

- `lastPrice`：最近一笔真实成交价。
- `bestBid`、`bestAsk`：当前最优买卖价。
- `referencePrice`：最近 5 分钟的成交量加权均价。
- 1 分钟 OHLCV：开、高、低、收、成交量和成交额。

`bestBid` 和 `bestAsk` 只取当前价格笼子内可成交的价格档。因参考价移动而暂时受保护的价格档仍显示在完整深度中，但必须带有不可成交标记，不能被市价单当作滑点报价来源。

无近期成交时，`referencePrice` 使用管理员基准价。新市场的默认价格发现门槛为 100 个最小交易单位。在累计有效成交量达到门槛前，参考价按下式从基准价平滑过渡到 5 分钟成交量加权均价：

`referencePrice = basePrice × (1 - discoveryRatio) + vwap5m × discoveryRatio`

其中 `discoveryRatio = min(累计有效成交量 / 价格发现门槛, 1)`。没有成交时该比例为零；达到门槛后，参考价完全由成交数据形成。管理员可以按市场提高门槛，但不能配置为少于 10 个最小交易单位。

行情事件可以逐笔发布给内部消费者，但玩家 GUI 最多每秒刷新一次。

## 10. 风险控制

全局默认值如下，市场可覆盖：

- 限价单价格笼子：参考价上下 20%。
- 市价单默认最大滑点：5%。
- 管理员允许玩家选择的最大滑点：20%。
- 一级熔断：5 分钟窗口内相对参考价波动达到 10%，暂停 2 分钟。
- 二级熔断：恢复后再次达到 20%，暂停 10 分钟并通知管理员。
- 玩家订单操作频率：每秒 5 次、每分钟 60 次。
- 自成交：拒绝新进入订单。

市场还必须配置最小/最大价格、最小报价单位、最小/最大单笔数量、单账户最大持仓、最大冻结资金和最大开放订单数。

价格笼子既检查新订单，也检查实际成交价。已经在订单簿中、但因参考价移动而落到当前笼子之外的订单继续保留原时间优先级，不过暂时不可成交；参考价重新覆盖该价格后自动恢复可成交状态。市价单确认时把相对滑点转换为固定的绝对最高买价或最低卖价，后续盘口变化不能扩大这个绝对边界。

熔断期间只允许查询和撤单。恢复后以熔断前参考价重新建立价格笼子。不存在每日固定涨跌停，也不存在固定闭市时间。

以下行为生成审计告警但不自动处罚：

- 高频双向互相成交。
- 极高撤单率或短时间反复挂撤。
- 多账户同步交易模式。
- 明显偏离市场规模的集中持仓或成交。

## 11. 资产存取与外部系统边界

交易所内部资产变化可以原子提交，但 Vault 和 Minecraft 背包不能与 SQL 组成同一个原子事务。所有跨边界存取都必须使用持久化转账状态机。

转账状态：

- `PREPARED`
- `PROCESSING`
- `COMPLETED`
- `FAILED`
- `REVIEW_REQUIRED`

### 11.1 资金存入

1. 写入带唯一 `transferId` 的 `PREPARED` 记录。
2. 串行化该玩家的经济操作，并调用经济适配器扣款。
3. 扣款成功后，在一个 SQL 事务中增加交易账户可用余额、写入账本并标记 `COMPLETED`。
4. 明确失败则标记 `FAILED`。
5. 外部扣款结果不明确则标记 `REVIEW_REQUIRED`，禁止自动重试。

### 11.2 资金提现

1. 在 SQL 事务中将可用余额转为待支付冻结余额并写入 `PREPARED` 记录。
2. 调用经济适配器向玩家付款。
3. 明确成功后扣除冻结余额、写入账本并标记 `COMPLETED`。
4. 明确失败时退回可用余额。
5. 结果不明确时进入 `REVIEW_REQUIRED`，不得自动重复付款。

Vault API 没有跨插件幂等事务 ID，因此不声称可以自动消除所有崩溃窗口。`REVIEW_REQUIRED` 是保守的人工恢复边界，优先避免重复扣款或重复付款。

### 11.3 物品存入与提现

- 存入前验证标准指纹、数量和物品状态。
- 使用唯一转账标记追踪跨背包和数据库的物品移动；内部转账标记不参与市场物品指纹。
- 背包空间不足时，提现保持在待领取状态，不向地面丢弃。
- 玩家重新登录时扫描未确认的转账标记，以完成或回滚中断操作。
- 无法自动判定的中断操作进入 `REVIEW_REQUIRED`，由财务恢复权限管理员处理。

## 12. 一致性、并发与恢复

- 每个市场只有一个串行撮合写入者。
- 同一账户跨市场操作按账户和资产键的稳定顺序获取数据库锁，避免死锁。
- 撮合产生的订单状态、余额、库存、成交、手续费和账本在同一 SQL 事务提交。
- 数据库是最终事实来源；内存订单簿只用于低延迟撮合。
- 数据库提交成功后更新内存状态；若内存更新失败或进程崩溃，从开放订单和市场序列重建。
- 数据库事务失败时将市场切换为 `RECOVERING`，暂停写入并重载。
- 插件正常关闭时停止接收新命令，排空撮合队列并保存市场序列。
- 紧急停机不撤销开放订单；重启后继续保留其价格和时间优先级。

每日核对：

- 各货币交易账户总负债。
- 各市场托管物品总量。
- 可用、冻结、待转账和系统账户之间的账本平衡。
- 开放订单冻结要求与实际冻结资产。

发现差额时立即暂停受影响市场并触发最高级别告警。

## 13. Bukkit/Folia 调度边界

- SQL、撮合、行情聚合和审计不在游戏线程执行。
- 背包读取和修改必须通过平台提供的正确实体/区域调度器执行。
- GUI 更新切回玩家对应的安全调度上下文。
- GUI 请求只提交不可变命令；不得直接持有或跨线程修改 Bukkit Inventory。
- 每次游戏线程回调目标小于 5ms。

## 14. 玩家界面与命令

主入口：`/quickshop exchange`，别名 `/qse`。

玩家界面：

- 市场列表：最新价、最佳买卖价、24 小时涨跌、成交量和状态。
- 市场详情：盘口、近期成交、持仓和开放订单。
- 下单：方向、限价/市价、数量、价格或最大滑点。
- 确认：预计成交范围、冻结资产、费率和最坏成交金额。
- 我的订单：开放、部分成交、完成和撤销记录。
- 资产中心：货币充值/提现、物品存入/领取和待处理转账。
- 历史记录：成交、手续费、资金和物品流水。

玩家确认市价单后，盘口变化不会扩大其滑点边界。超出边界的剩余数量按 IOC 自动取消。

管理员功能：

- 创建、启用、暂停、恢复和关闭市场。
- 强制撤销异常订单。
- 查看异常交易和待处理转账。
- 处理 `REVIEW_REQUIRED` 转账。
- 执行账本核对并导出审计报告。
- 设置市场限额和是否允许对应物品创建普通箱子商店。

历史订单、成交和账本不可由管理命令直接修改。

## 15. 权限

至少提供以下权限边界：

- `quickshop.exchange.use`
- `quickshop.exchange.deposit`
- `quickshop.exchange.withdraw`
- `quickshop.exchange.order.limit`
- `quickshop.exchange.order.market`
- `quickshop.exchange.admin.market`
- `quickshop.exchange.admin.orders`
- `quickshop.exchange.admin.recovery`
- `quickshop.exchange.admin.audit`

财务恢复和审计权限不得隐含在普通市场管理权限中。

## 16. 可观测性

指标包括：

- 每个市场的命令队列长度和撮合延迟。
- SQL 提交延迟和失败率。
- 开放订单、成交量、成交额和拒单原因。
- 熔断次数与持续时间。
- 待处理及 `REVIEW_REQUIRED` 转账数量。
- 账本核对差额。
- GUI 请求量和游戏线程回调耗时。

关键管理操作、转账恢复和强制撤单必须记录操作者、时间、原因和前后状态。

## 17. 测试策略

### 17.1 撮合单元测试

- 价格优先和时间优先。
- Maker 成交价。
- 部分成交和跨价格档成交。
- GTC、IOC、撤单和撤单重建。
- 限价、市价和滑点边界。
- 手续费、报价单位和舍入。
- 自成交阻止和市场状态。

### 17.2 资产性质测试

随机生成下单、成交、撤单、存取和失败序列，持续验证：

- 任何余额和库存都不为负。
- 不发生超卖或超额买入。
- 每个资产的复式账本始终平衡。
- 撮合前后资产总量守恒，手续费只流入系统费用账户。
- 重复 `requestId` 不改变第二次状态。

### 17.3 仓储与故障注入

- SQLite 和 MySQL 集成测试。
- 在每个 SQL 提交点注入失败。
- 在每个外部转账状态间模拟进程终止。
- 从开放订单重建订单簿并保持原优先级。
- 模拟数据库断线、慢查询和事务冲突。
- 模拟 Vault 失败、玩家离线、背包已满和重复 GUI 点击。

### 17.4 平台测试

- Paper 与 Folia 测试服验证调度线程。
- GUI 刷新、玩家退出、服务器关闭和插件重载。
- 自定义物品指纹和普通箱子商店共存。

## 18. 性能验收基线

参考环境为 4 个 CPU 核心、同机或低延迟 MySQL：

- 100 个活跃市场。
- 总计 100,000 个开放订单。
- 持续每秒 200 个订单操作。
- 撮合核心 P95 小于 20ms。
- 包含数据库提交的订单确认 P95 小于 100ms。
- 游戏线程单次处理小于 5ms。

性能基线用于回归和容量规划，不代表在任意硬件与任意第三方数据库上的保证。

## 19. 上线策略

1. 功能默认关闭，在测试服使用测试货币和少量普通材料。
2. 正式服仅对白名单开放，采用较低持仓和订单限额，观察至少一个完整经济周期。
3. 核对账本、熔断、成交质量和玩家反馈后逐步开放并提高限额。

上线不迁移箱子商店、不导入其历史价格，也不自动取消现有商店。管理员可以逐个市场决定是否禁止对应物品继续创建普通商店。

## 20. 未来跨服路线

首版接口必须允许将 `MatchingEngine`、`ExchangeRepository` 和行情发布迁出 Minecraft 进程。跨服版本需要：

- MySQL 作为共享事实来源。
- 每市场撮合租约、主节点选举和 fencing token。
- 子服到撮合服务的认证命令通道。
- 可重放的成交与行情事件流。
- 跨服请求幂等和统一账户锁定。

在跨服版本完成前，只允许一个插件实例启用撮合写入；其他子服不得直接共享并写入同一订单簿数据库。
